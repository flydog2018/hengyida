## 1. 测试策略总纲

### 1.1 测试目标

围绕架构公式「一份 Schema + 三个消费者（designer / runtime / server-core）+ 两个部署形态」，测试的核心目标是**守住三条主线**：

1. **契约主线**：designer 产出的 FormSchema 必须能被 runtime 正确渲染、被 server-core 正确执行；JSON 配置导入导出必须 100% 往返还原——契约是唯一耦合点，一旦破坏全线崩溃。
2. **数据主线**：动态建表（DDL）幂等且不丢数据；服务端权威计算（公式/校验/权限）不可被客户端篡改；行级权限谓词注入必须无越权泄露。
3. **体验与合规主线**：满足全部可量化指标（首屏<2s、拖拽≥50FPS、发布≤10s、TTFV≤30min）、原创性留痕齐全、浏览器兼容与安全基线达标。

### 1.2 测试原则

| 原则 | 说明 |
| --- | --- |
| 测试左移 | 在 T02 契约冻结（M1）时即介入 Schema/API 契约测试设计，不等到 T05 才测试 |
| 分层隔离 | 单元层纯逻辑快测；集成层注入真实 DB；E2E 只覆盖关键黄金路径，避免用 E2E 测边界 |
| 契约先行 | SchemaEnvelope / FormSchema / OpenAPI 是测试的第一公民，任何字段变更先过契约测试 |
| 服务端权威 | 安全与公式测试一律以「绕过前端直接打 API」方式验证，不信任客户端展示结果 |
| 可判定性 | 每条用例必须有明确的前置、步骤、预期与量化阈值，杜绝「看起来正常」式主观断言 |
| 独立幂等 | 用例自带测试数据（工厂/Fixture），可任意顺序、可重复执行，不依赖人工清理 |

### 1.3 分层模型（测试金字塔）

```text
                /\
               /  \   L4 E2E（设计器→发布→填报黄金路径，少量）
              / L5-7\  性能 / 兼容 / 安全（专项）
             /------\
            /  L3 集成 \  引擎 + DB + API 全链路（中量）
           /----------\
          /  L2 契约测试 \  Schema / API 契约（中量）
         /--------------\
        /    L1 单元测试    \  公式 / 权限 / Schema / 编译（大量、快）
       /--------------------\
```

越靠底层数量越多、运行越快、定位越准；E2E 只保留覆盖核心用户故事的黄金路径。

## 2. 测试分层、工具建议与覆盖目标

### L1 · 单元测试（Unit Tests）

| 项目 | 内容 |
| --- | --- |
| 测试目标 | 验证纯领域引擎与工具函数的正确性、边界与安全，快速失败、精准定位 |
| 测试对象 | `shared/utils/formula-ast.ts`、`server/core/formula-engine/*`、`server/core/permission-engine/*`、`server/core/schema-engine/*`、`designer/engine/ConfigCompiler.ts`、`designer/src/utils/id.ts`、`designer/engine/SchemaValidator.ts` |
| 工具建议 | **Vitest 1.x**（TS 原生、快，与 Vite 同源）；NestJS 服务端纯函数亦可用 Vitest；断言用 Vitest 内置 + `vitest-faker` 造数 |
| 覆盖目标 | 核心引擎语句/分支覆盖率 **≥ 80%**（公式、权限、Schema 迁移三个模块 **≥ 90%**）；100% 覆盖公开函数 happy path + 关键异常路径 |
| 关键断言点 | 公式求值结果精度、AST 白名单拒绝、`eval/new Function` 不存在、权限逐级短路顺序、Schema 校验正反例、ID 稳定性、编译产物结构 |

### L2 · 契约测试（Contract Tests：Schema / API）

| 项目 | 内容 |
| --- | --- |
| 测试目标 | 守住「designer 产出 ↔ runtime 消费 ↔ server 执行」的唯一连接点，防止契约漂移 |
| 测试对象 | `SchemaEnvelope` 结构与 `schemaVersion`、FormSchema 字段与 `binding.column` 派生、`widget-registry` 控件契约、统一响应 `{code,data,message}`、错误码分段、`X-Schema-Version` 头、OpenAPI 3.0 契约 |
| 工具建议 | **Ajv 8**（JSON Schema 校验，与代码同源）；**Vitest** 组织用例；**Supertest** 校验 API 响应契约；API 契约一致性用 **Swagger/OpenAPI diff**（如 `openapi-diff`）；Pact 类工具可选（跨端契约） |
| 覆盖目标 | 全部 Schema 类型 100% 有 JSON Schema 校验用例；导入导出往返还原率 **100%**；所有 API 响应结构符合 `{code,data,message}` **100%** |
| 关键断言点 | 导出→导入后深比较（含字段 id/label/校验/显示条件/子表/关联/公式/权限）一致；版本迁移逐级正确；不兼容版本明确报错；控件注册表单向覆盖 designer 与 runtime 用到的全部 widget |

### L3 · 集成测试（Integration：引擎 + DB + 模块）

| 项目 | 内容 |
| --- | --- |
| 测试目标 | 验证引擎间协作与真实数据库交互，覆盖发布链路与数据链路 |
| 数据库矩阵（v1.1 锁定） | **一期只跑 MySQL 8.0**；PostgreSQL / SQL Server 方言抽象层**仅做代码级静态检查**（接口实现完整、无硬编码 MySQL 语法），**不实际起库执行** |
| 测试对象 | `publish` 用例（校验→版本+1→DDL→保存 Schema）、`data-engine` 动态 DDL（ensureTable/evolveTable 幂等）、MySQL 8.0 方言（唯一实测）、填报链路（权限→公式→校验→行级过滤→落库）、列表筛选/排序/分页、Excel 导入导出（Excel 部分为【波次2】） |
| 工具建议 | **Vitest + Supertest**（API 集成）；**Testcontainers** 或独立 `docker-compose` 拉起 **MySQL 8.0** 测试实例（一期唯一 DB 实例）；每个用例事务回滚或独立库，保证幂等；**knex migrate** 辅助建库 |
| 覆盖目标 | 动态建表自动化 **100%**（零手工 DDL）；发布链路、填报链路两条主链路 100% 覆盖；DDL 幂等与增量演进（不丢数据）必测 |
| 关键断言点 | 发布后物理表/列生成正确且重复发布幂等；新增字段只 `ALTER ADD COLUMN` 不重建表；服务端公式落库正确且忽略客户端伪造值；行级谓词注入后查询结果仅含授权行；Excel 错误行定位准确（【波次2】） |

### L4 · 端到端测试（E2E：设计器 → 发布 → 填报）

| 项目 | 内容 |
| --- | --- |
| 测试目标 | 以真实用户视角验证核心用户故事 US-01~US-10 的黄金路径贯通 |
| 测试对象 | 建应用→拖 3 字段→发布→填报（TTFV）；字段属性/显示条件生效；子表/关联表/公式填报；三角色登录与越权；PC/H5 数据一致 |
| 工具建议 | **Playwright 1.40+**（跨 Chromium/Firefox/WebKit，支持移动端 emulation）；**@testing-library/react** 辅助组件级交互验证；Page Object 模式组织；CI 中 headless 执行 |
| 覆盖目标 | 覆盖 US-01~US-10 全部 10 条黄金路径；**不**在 E2E 中堆砌边界用例（边界下沉到 L1/L3） |
| 关键断言点 | 发布≤10s（打点计时）；首屏<2s（P95）；H5 触控可用且数据一致；越权被拒且无数据泄露；显示条件按值动态显隐 |

### L5 · 性能测试（Performance）

| 项目 | 内容 |
| --- | --- |
| 测试目标 | 量化验证全部性能指标，防止体验退化 |
| 测试对象 | 设计器拖拽帧率、runtime 首屏、发布耗时、API 并发与吞吐、TTFV |

| 关键断言点 | 各指标取多次采样 P95 而非单次；性能回归设基线阈值，超阈值 CI 红灯 |

### L6 · 兼容性测试（Compatibility）

| 项目 | 内容 |
| --- | --- |

### L7 · 安全测试（Security）

| 项目 | 内容 |
| --- | --- |

### 6.4 非功能门禁实现方式

- **注释率**：以脚本统计有效注释行 / 总代码行（排除空行与自动生成文件），阈值 > 30%，纳入 CI。
- **README 齐全**：清单列出关键模块（每个 workspace 包 + 四个 core 引擎 + deploy），逐一检查存在性与关键章节（职责/接口/用法）。
- **原创性留痕**：核对 `originality-checklist.md` 每条决策含「参照来源=self/original、决策理由、日期」；扫描禁用竞品专有名词。

## 7. 智能路由判定（Smart Routing）

> 每次测试执行后必须进行路由判定，明确责任归属，避免无谓扯皮。严格执行 **最多 2 轮** 规则。

### 7.1 判定规则

| 路由目标 | 判定条件 | 处理方式 |
| --- | --- | --- |
| **Engineer（工程师 Alex）** | 断言符合 PRD/架构预期，但实际输出错误 → **源码 Bug** | 提交缺陷报告：失败用例编号、期望 vs 实际、源文件与函数、错误堆栈/复现步骤，交工程师修复 |
| **QA（自修）** | 源码行为正确，但测试用例断言/前置/数据错误 → **测试 Bug** | 自行修正测试用例，不计入源码缺陷；修正后重跑 |
| **NoOne** | 全部用例通过 | 输出成功报告，结束 |

**决策口诀**：断言对、结果错 → 找工程师；断言错、结果对 → 自己改；都对 → 收工。

### 7.2 缺陷报告最小要素（发工程师）

- 失败用例编号与所属层次（如 TC-14 / L3）
- 期望行为（引用 PRD/架构条款）与实际行为
- 涉及源文件与函数（如 `server/core/formula-engine/evaluate`）
- 复现步骤、输入数据、错误码/堆栈、截图或日志
- 严重级别（P0/P1/P2）与阻塞影响

### 7.3 最多 2 轮测试规则（硬限制）

```text
Round 1：编写/补齐测试 → 执行 → 分析结果 → 路由
   ├─ 全通过        → 路由 NoOne，输出成功报告，结束
   ├─ 源码 Bug      → 报工程师修复，等待修复后进入 Round 2
   └─ 测试 Bug      → QA 自修，修正后重跑（计入 Round 1 收尾）

Round 2：工程师修复后（或自修后）回归测试 → 分析结果 → 路由
   ├─ 全通过        → 路由 NoOne，输出成功报告，结束
   └─ 仍有失败      → 立即停止，不再进入 Round 3；
                       将全部剩余问题写入最终报告「Known Issues」，随版本交付并登记后续计划
```

**原则**：两轮为硬上限，防止无限调试拖慢交付；剩余边缘问题以文档化方式交接，而非无休止返工。

### 7.4 测试报告格式

```markdown
# 测试报告
## Summary
- 总用例 / 通过 / 失败 / 跳过；各层通过率；覆盖率
- 路由决策：NoOne / Engineer / Known Issues
## 失败用例（如有）
- 用例编号：期望 X，实际 Y — [源文件/函数；严重级别]
## Known Issues（Round 2 仍有失败时）
- 问题描述 + 影响模块 + 后续计划
```

## 8. 风险与测试盲区

| 编号 | 风险/盲区 | 说明 | 缓解措施 |
| --- | --- | --- | --- |
| RK-01 | **原创性主观判定** | 「不模仿竞品」难以自动化判定，工具无法量化 | 建立 checklist + 人工评审签字；记录每项决策的参照来源与理由；扫描竞品专有名词；评审留存会议纪要 |
| RK-02 | **跨数据库动态 DDL** | Phase1 仅 MySQL，PG/SQL Server 方言未实测，切换存在隐患 | Phase1 只承诺 MySQL 矩阵；Dialect 接口单测覆盖抽象契约；Phase2 起建 PG/SQL Server 兼容测试矩阵；DDL 一律幂等、只增不删 |
| RK-03 | **公式边界与语义歧义** | 精度、除零、空值、类型隐式转换等边界难穷举 | 建立边界用例集（TC-03）；公式白名单函数逐项单测；精度统一由服务端控制；无法穷举的组合登记为 Known Issues |
| RK-04 | **移动端碎片化** | 真机/系统/浏览器组合爆炸，emulation 无法覆盖全部 | Playwright 主流视口矩阵 + 真机抽检关键场景；聚焦触控区域/单列/输入方式三类核心适配点；明确不支持 IE |
| RK-05 | **性能数据受环境影响** | FPS/首屏耗时受机器与网络波动影响，单次结果不可靠 | 多次采样取 P95；固定基线环境；设阈值区间与回归基线；CI 中隔离噪音 |
| RK-06 | **E2E 脆弱性** | UI 变更易导致 E2E 失败（假阳性） | Page Object 模式 + 稳定 data-testid 选择器；E2E 只覆盖黄金路径，边界下沉 L1/L3；失败先按第 7 节判定是否测试 Bug |
| RK-07 | **权限组合爆炸** | 角色×应用×表单×行级×字段级组合极多 | 用判定矩阵/参数化测试覆盖关键组合；逐级短路逻辑做单测；字段级为 Phase2 项，本期仅断言「未越级」 |
| RK-08 | **测试数据与状态污染** | 动态建表/数据用例易互相污染 | Testcontainers 独立实例 + 事务回滚 + 工厂造数；用例幂等可重复 |
| RK-09 | **并发与幂等边界** | 并发发布/并发建表可能出现竞态 | k6 并发专项（TC-12 扩展）；DDL 幂等设计；并发问题登记并评估加锁 |
| RK-10 | **测试盲区：主观体验** | 视觉美观、交互流畅的主观部分无法完全自动化 | 人工验收 checklist 补充；以可量化指标（FPS/耗时/布局尺寸）替代主观描述 |
| RK-11 | **严格单人投入下测试时间被压缩（v1.1 新增）** | 团队投入受限（小团队/单人 QA），12 周 + 2 周缓冲内覆盖波次1+波次2 全部用例的时间压力大，易出现测试被挤压或走过场 | 按波次分层取舍：**波次2 用例可顺延**（Excel、行级权限细化、H5 深度触控、性能专项、Docker 在缓冲期内补齐）；**波次1 核心用例不可裁剪**（动态建表、发布、公式/权限安全、JSON 往返、列表、角色/应用表单级权限必须 100% 执行）；测试左移随交付同步编写，避免末期集中赶工；必要时缩窄浏览器/视口组合但保住黄金路径 |
